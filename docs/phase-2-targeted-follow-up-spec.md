# Phase 2：基于已有学生信息的针对性补问

## 1. 目标与范围

在生成 UC PIQ 推荐前，系统先判断现有学生证据是否足以支持可靠评分。只有当缺失信息可能改变 PIQ 的推荐、排序或 Match Score 时，系统才提出针对性问题。

本阶段的用户补充信息只用于当前推荐会话，不更新学生档案、不写入 `.docx`、不重建 Chroma 索引。

本阶段只接入 UC PIQ。Common App、学生画像持久化、PIQ 四篇组合优化、College/Major 推荐均不在本阶段实施范围内。

## 2. 设计原则

1. 先使用已有信息，再决定是否补问。
2. 只问会影响推荐决策的问题，不为丰富文书细节而追问。
3. 问题必须指向一个明确经历和一个明确缺口。
4. 补问信息与档案信息分开标记，不能伪造 Experience 编号或标题。
5. 不要求资料完美；达到“足以推荐”即可停止。
6. 用户可以跳过、拒绝或直接要求推荐。
7. 达到轮数上限后必须给出当前证据下的推荐，不得无限追问。
8. 敏感经历只询问评估题目适配度所需的非敏感信息，不鼓励披露隐私。

## 3. 信息模型

每项候选经历按以下结构评估。Phase 2 可以先使用内存或请求级数据，不要求数据库持久化。

```json
{
  "experience_ref": {
    "number": 2,
    "title": "Computer Science Journey"
  },
  "source": "profile | session",
  "student_action": {
    "value": "学生本人具体做了什么",
    "status": "known | partial | missing"
  },
  "outcome_or_impact": {
    "value": "产生了什么结果、影响或变化",
    "status": "known | partial | missing"
  },
  "reflection_or_growth": {
    "value": "学生学到了什么、如何改变、体现什么价值",
    "status": "known | partial | missing"
  },
  "context_or_challenge": {
    "value": "理解行动所必需的背景或困难",
    "status": "known | partial | missing"
  },
  "demonstrated_traits": ["curiosity", "initiative"],
  "confidence": "high | medium | low"
}
```

规则：

- 档案已有经历保留原始 `Experience N: Title`。
- 只有会话中出现的新经历，其 `experience_ref` 为 `null`，展示时使用“你刚才提到的经历”等自然表述。
- `source=session` 的内容不能被描述为“学生档案显示”。
- 不从其他经历借用行动、结果或反思来填补当前经历。
- 未明确提供的信息保持 `missing`，不能由模型推断成事实。

这份结构将来可直接扩展为学生画像的输入格式，但 Phase 2 不执行写回。

## 4. 信息是否充足

### 4.1 单项经历的最低充分条件

一项经历满足以下条件时，通常足以评估其对应 PIQ：

- `student_action` 为 `known`；并且
- `reflection_or_growth` 为 `known`；并且
- `outcome_or_impact` 至少为 `partial`，或者该 PIQ 本身不依赖外部影响；并且
- 已有信息足以区分该经历更适合哪些 PIQ，而不是只有一个主题关键词。

例如，“参加过 AI Research”不充分；“负责清洗数据和比较模型，最终发现原方案存在偏差，并由此学会质疑实验假设”通常充分。

### 4.2 整体推荐的充分条件

满足以下任一条件时直接推荐：

1. 至少有足够数量的候选 PIQ 达到 7.0 分以上，且证据能支持其排序；
2. 当前缺口即使补齐，也不太可能改变入选 PIQ 或相邻候选的排序；
3. 用户问的是某一道 PIQ 的解释、比较或适配性，而现有证据已足以直接回答；
4. 用户明确要求不要追问、跳过问题或直接推荐；
5. 已达到最大补问轮数。

“足够数量”取用户要求的推荐数量；用户未明确数量时沿用现有默认数量逻辑。

### 4.3 资料不足的判定

只有同时满足以下条件，才进入补问：

- 某个高潜力候选经历缺少关键字段；
- 缺失字段可能使候选 PIQ 的 Match Score 改变至少约 1 分，或改变入选/排序结果；
- 用户能够合理回答该问题；
- 问题不要求不必要的敏感信息。

这里的“约 1 分”是决策阈值，不要求在界面展示为精确预测。

## 5. 哪些缺口值得问

优先级从高到低：

1. 学生本人具体做了什么；
2. 经历为何对学生重要，学生学到了什么或如何改变；
3. 行动产生了什么结果、影响或可观察变化；
4. 为理解行动所必需的困难、选择或责任范围。

通常不值得问：

- 额外的故事细节或场景描写；
- 已经明确的影响对应的精确数字；
- 日期、工具、编程语言、组织全名；
- 只会让文章更生动、但不会改变 PIQ 适配判断的信息；
- 为满足“信息完整”而机械补齐所有字段。

## 6. 问题生成规则

每个问题必须包含：

- 明确指向已有 Experience 编号和标题，或明确引用用户刚提到的新经历；
- 只询问一个主要信息缺口；
- 说明需要的是学生本人的行动、结果或反思，而非泛泛介绍；
- 允许用户跳过或直接推荐。

推荐写法：

> 关于 Experience 3: AI Research，我已经知道你参与了研究，但还不知道你本人负责了什么。你能简要说明你做出的一个具体决定或完成的一项核心工作吗？如果不想补充，也可以让我直接根据现有资料推荐。

禁止写法：

> Can you tell me more about this experience?

### 6.1 每次问题数量

- 默认一次问 1 个问题。
- 只有两个问题属于同一经历、用户可一次简短回答，且两者都可能改变推荐时，最多一次问 2 个。
- 不在同一轮同时询问多个不同经历。

### 6.2 候选问题选择

当存在多个缺口时，选择“预期决策价值”最高的问题：

```text
决策价值 = 改变入选或排序的可能性 × 对评分维度的影响 × 用户可回答性
```

该公式用于排序思路，不需要模型输出数值。

优先询问位于入选边界附近的候选。例如第四名与第五名证据接近时，优先问能区分这两项的信息，而不是继续完善已经明显排第一的经历。

## 7. 轮数与停止条件

- 通常在 1–3 个有效问题后停止。
- 每次只问 1 个问题。
- 可配置硬上限默认为 5，防止意外循环。
- 用户回答后重新评估全部候选 PIQ，而不是只评估被追问的 PIQ。
- 第二轮仍不足时，不再继续追问；输出当前证据下的推荐及简短限制说明。

立即停止补问的条件：

- 已达到整体推荐充分条件；
- 用户说“不知道”“没有”“跳过”“直接推荐”等；
- 用户回答与问题无关，重新表达一次仍无法获得有效信息；
- 后续缺口只影响文书质量，不影响推荐决策；
- 继续询问可能引导用户披露不必要的敏感信息；
- 达到可配置硬上限（默认 5 个问题）。

用户跳过某一问题后，本次会话不应以不同措辞重复询问同一缺口。

## 8. 状态机

```text
RETRIEVE_PROFILE
    ↓
ASSESS_SUFFICIENCY
    ├─ sufficient ───────────────→ RECOMMEND
    ├─ user_requests_direct ─────→ RECOMMEND
    └─ material_gap
            ↓
        ASK_TARGETED_QUESTION
            ↓
        RECEIVE_SESSION_EVIDENCE
            ↓
        REASSESS_ALL_CANDIDATES
            ├─ sufficient ───────→ RECOMMEND
            ├─ next question has decision value ─→ ASK_TARGETED_QUESTION
            └─ stable or hard limit reached ─────→ RECOMMEND_WITH_LIMITATION
```

每个 PIQ 会话至少保存：

```json
{
  "profile_id": "...",
  "mode": "uc_piq",
  "follow_up_round": 1,
  "asked_gap_ids": ["experience_3.student_action"],
  "session_evidence": [],
  "status": "assessing | awaiting_answer | ready"
}
```

## 9. 与现有系统的集成边界

### 9.1 后端

现有 `/api/recommend` 返回纯文本流，无法可靠表达“这是问题还是最终推荐”的结构化状态。实施时建议让 PIQ 流程先经过一个轻量决策层，并返回以下状态之一：

- `needs_follow_up`：返回问题、缺口标识和当前轮数；
- `ready`：开始现有推荐流；
- `recommend_with_limitations`：达到停止条件后开始推荐流。

可以扩展现有 API，也可以新增 PIQ 专用的评估端点；不应复用 College/Major 的偏好字段。

推荐请求必须继续携带当前会话的 `session_evidence`。后端组装模型上下文时分为：

```text
STUDENT EVIDENCE（来自 RAG）
SESSION EVIDENCE（来自本次会话）
RECENT CONVERSATION（仅用于理解上下文）
```

### 9.2 前端

前端需要区分两种 assistant 输出：

- 针对性问题：显示正常问答界面，可提供“跳过并直接推荐”；
- 最终推荐：沿用现有 Markdown 流式展示和 Match Score。

不要仅依赖自然语言判断输出类型；应使用后端结构化状态。

### 9.3 未来学生画像

Phase 3 可以消费 `session_evidence`，增加以下步骤：

```text
提取候选事实 → 与现有档案去重/冲突检测 → 用户确认 → 写入画像 → 重建或增量更新索引
```

Phase 2 不调用这条写入链路。这样既能独立上线，又能保留将来的复用能力。

## 10. 评分与补问的关系

- Phase 1 的 Match Score 仍只由 Prompt Fit、Evidence Depth、Personal Insight 组成。
- “是否需要补问”不是第四个评分维度。
- 多样性仍不计入单篇 Match Score。
- 用户补充有效证据后，可以重新计算分数。
- 同一份证据下，同一 PIQ 的分数不应因是否处于补问流程而变化。
- 资料不足不等于自动低分；应按已证实证据评分，并用缺口判断是否值得补问。

## 11. 示例

### 示例 A：缺少学生行动

已有资料：

> Experience 3: AI Research。学生参加了一个人工智能研究项目。

判断：主题与 PIQ #6 可能相关，但无法判断学生贡献和证据深度。

问题：

> 关于 Experience 3: AI Research，你本人在项目中负责了哪项核心工作，或者做过哪个重要决定？

### 示例 B：行动明确，缺少反思

已有资料：

> 学生设计实验、清洗数据并完成结果比较。

判断：行动充分，但尚不清楚经历揭示了什么个人洞察。

问题：

> 完成这些实验后，你对研究、人工智能或自己的思考方式有了什么新的认识？

### 示例 C：无需补问

已有资料：

> 学生发现团队实验存在数据偏差，主动重新设计数据处理流程，使结果更稳定；这让学生认识到研究中质疑假设比快速得到答案更重要。

判断：行动、结果和反思均足以评估，直接推荐。

### 示例 D：用户拒绝补充

用户：

> 我不记得了，直接推荐吧。

行为：不重复问题，基于现有证据推荐，并在相关 PIQ 下简短说明证据限制。

### 示例 E：敏感经历

已有资料：

> 用户提到曾经历抑郁，但没有提供其他信息。

行为：不询问诊断、治疗或创伤细节。只在用户主动询问题目适配性时，询问其愿意分享的行动、认识或成长；用户不愿补充则立即停止。

## 12. 验收标准

1. 资料充分时不出现多余问题，直接生成 PIQ 推荐。
2. “参加过 AI Research”会触发针对学生本人行动的具体问题。
3. 系统不会输出泛泛的“请多介绍一下这段经历”。
4. 默认每轮 1 个问题，任何一轮不超过 2 个。
5. 通常在 1–3 个问题后停止，达到默认 5 个问题的硬上限后一定生成推荐。
6. 用户选择跳过后，系统不会重复询问同一缺口。
7. 会话补充信息会参与当前 PIQ 评分和推荐。
8. 会话补充信息不会写入学生档案或 Chroma。
9. 会话中新经历不会获得虚构的 Experience 编号或标题。
10. 问题只针对可能改变推荐、排序或评分的关键缺口。
11. Match Score 继续保持 0–10、一位小数，且不包含多样性。
12. 敏感经历不会触发不必要的隐私追问。

## 13. 建议实施顺序

1. 定义 PIQ 会话状态、缺口和 session evidence 的后端 schema。
2. 实现确定性的轮数、跳过和停止规则。
3. 增加 AI 信息充分度评估器，并要求结构化输出。
4. 将 session evidence 作为独立区块加入推荐上下文。
5. 前端增加针对性问题状态和“跳过并直接推荐”。
6. 增加单元测试、状态机测试和端到端场景测试。

当前默认值为每次 1 个问题、通常 1–3 个问题后停止、硬上限 5；硬上限可通过环境变量配置。
